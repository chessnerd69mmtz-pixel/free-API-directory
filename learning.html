1. What is an API?

An API (Application Programming Interface) is a defined way for one program to ask another program for data or an action. Think of it as a contract: the client sends a request in an accepted format, and the server returns a response.

Client

Your website, script, mobile app, or backend that makes the request.

Endpoint

A URL representing a particular operation or resource, such as /users or /weather.

Request

Method + URL + optional query/body + headers.

Response

Status code + headers + usually a JSON body.

Example: a weather request

GET https://api.example.com/weather?city=Bengaluru

The server might respond with JSON containing temperature, humidity, and a forecast. Your application can then turn that raw data into a card, chart, alert, or recommendation.

Key idea: An API is not the same thing as a website. A website is designed for humans to read; an API is designed for software to exchange structured data or trigger actions.
Check yourself: Which part tells a server which operation you want?
Usually the HTTP method plus the endpoint. For example, GET /users asks to retrieve users, while POST /users commonly asks to create one.

2. How HTTP requests work

Most web APIs use HTTP. The method communicates intent. The URL identifies the target. Headers carry metadata, and a body can carry data for methods such as POST, PUT, or PATCH.

MethodTypical purposeExample
GETRead dataGET /books/42
POSTCreate or trigger an operationPOST /messages
PUTReplace/update a resourcePUT /users/42
PATCHPartially update a resourcePATCH /users/42
DELETERemove a resourceDELETE /users/42

Query parameters vs request body

Query parameters commonly refine a request, such as ?page=2&limit=20. A JSON body is commonly used when sending structured data to POST/PUT/PATCH endpoints.

curl "https://api.example.com/books?limit=10" \
  -H "Accept: application/json"
Practice: Open the API Playground and try a documented public endpoint. Browser requests can fail because of CORS, authentication, or provider policy; that failure itself is useful debugging information.

3. JSON, status codes, and responses

JSON is a common format for API responses because it represents objects, arrays, strings, numbers, booleans, and null in a machine-readable form.

{
  "city": "Bengaluru",
  "temperature_c": 27.4,
  "conditions": "Cloudy",
  "alerts": []
}

Read the status code before trusting the body

2xx

Success. 200 is common for a successful GET; 201 commonly means created.

4xx

Client/request problem. 401 often means authentication is missing or invalid; 429 commonly means rate limiting.

5xx

Server-side failure. The provider may be temporarily unable to complete a valid request.

Robust client logic

const response = await fetch(url);
if (!response.ok) throw new Error("API returned HTTP " + response.status);
const data = await response.json();
console.log(data);
Habit: Do not blindly assume a response has every field. APIs evolve. Validate important fields and handle missing, null, or unexpected values.

4. Authentication and API keys

Authentication tells a provider who or what is making a request. Common patterns include API keys, bearer tokens, OAuth access tokens, signed requests, and completely keyless endpoints.

Three common patterns

// API key in a custom header
X-API-Key: YOUR_KEY

// Bearer token
Authorization: Bearer YOUR_TOKEN

// Query parameter (only when explicitly documented)
?api_key=YOUR_KEY
Security rule: Never paste a real secret into source code, screenshots, public issues, or a public Git repository. A frontend application cannot safely hide a private server credential from its users.

Server-side credentials

# .env
API_KEY=replace-with-your-secret

# application code
const key = process.env.API_KEY;

For a browser-only application, prefer a key specifically designed for public/browser use, provider-supported domain restrictions, or a backend proxy. Follow the provider's current documentation.

Scenario: Your public GitHub repository contains const API_KEY = "sk-...". What should you do?
Remove the exposed key from the code/history where appropriate, revoke or rotate it with the provider, and replace it with a safer credential flow. Deleting the visible line alone does not make an exposed secret safe.

5. Understanding free tiers, quotas, and limits

“Free API” can mean a permanently free quota, a temporary trial, free credits, a community endpoint, or a limited free plan with conditions.

TermWhat to investigate
Requests/monthHow many calls are included over the billing period?
Requests/dayIs there a daily cap even when monthly capacity remains?
Rate limitHow many requests can be made per second/minute?
TokensFor AI APIs, is quota measured in input/output tokens rather than requests?
CreditsAre credits recurring, one-time, promotional, or tied to a payment method?

Do the math

If your app makes 20 requests per user per day and you expect 100 active users:

20 × 100 × 30 = 60,000 requests/month

A “100,000 requests/month” allowance could cover that workload in raw request count, but you still need to check rate limits, endpoint-specific quotas, authentication, data restrictions, and terms.

Directory principle: Treat “free” as a claim that needs evidence. Open the provider's current official pricing/limits page before designing around a critical quota.

6. How to choose an API

Do not choose solely because a provider is free. Start with the requirements of the feature you are building.

1. Capability

Does the API provide the operation and data you need?

2. Access

Key, OAuth, account, card, IP restrictions, CORS, or keyless?

3. Limits

Will quota and rate limits cover your expected workload?

4. Terms

Check commercial use, attribution, redistribution, retention, and data restrictions.

5. Reliability

Look for documentation quality, status information, change history, and evidence freshness.

6. Exit plan

Can you replace the provider if pricing, limits, or availability changes?

Selection workflow

  1. Describe the feature in one sentence.
  2. Use Use Cases to discover relevant providers.
  3. Use Finder to narrow authentication, free-tier, card, and verification constraints.
  4. Open the provider profile and read evidence/source links.
  5. Read the provider's own docs and pricing.
  6. Prototype one real request before committing your architecture.

7. Build your first integration

Start small: one endpoint, one successful response, one useful transformation. Then add retries, validation, caching, logging, and user-facing error handling.

JavaScript example

async function getWeather(city) {
  const url = "https://api.example.com/weather?city=" + encodeURIComponent(city);
  const response = await fetch(url);
  if (!response.ok) throw new Error("Weather API failed: HTTP " + response.status);
  const data = await response.json();
  if (typeof data.temperature_c !== "number") throw new Error("Unexpected API response");
  return { city, temperature: data.temperature_c };
}

What production code adds

  • Timeouts so a hung request does not freeze your UI forever.
  • Retries only where retrying makes sense, often with exponential backoff.
  • Rate-limit handling for HTTP 429.
  • Input and output validation.
  • Logging that excludes secrets and sensitive payloads.
  • Caching where stale data is acceptable.
  • A fallback provider if the feature is business-critical.
Build rule: Keep provider-specific code behind a small adapter function. Changing providers should not require rewriting your entire application.

8. Debug API failures systematically

When an API call fails, identify which layer failed instead of randomly changing code.

SymptomFirst things to check
401 UnauthorizedKey/token exists, correct header format, correct environment, expired/revoked credential.
403 ForbiddenPermissions, plan restrictions, domain/IP restrictions, endpoint access, account status.
404 Not FoundBase URL, endpoint path, API version, resource identifier.
409 ConflictState conflict or duplicate resource; read the endpoint documentation.
429 Too Many RequestsRate limit, Retry-After header, concurrency, quota window.
5xxProvider outage or transient server failure; check provider status/docs.
Browser CORS errorThe browser may be blocked before your code can read the response. Test from a permitted backend or documented browser flow.
Quick quiz: cURL works but the browser fails with a CORS error. Which conclusion is safest?

9. API security checklist

  • Keep server secrets in environment/secret management systems.
  • Rotate credentials after suspected exposure.
  • Use least-privilege permissions where supported.
  • Do not log Authorization headers or full sensitive request bodies.
  • Validate untrusted user input before sending it to an API.
  • Set request timeouts and sensible size limits.
  • Use HTTPS and follow provider security requirements.
  • Review data retention and privacy terms for sensitive workloads.
Important: Browser local storage can be useful for a personal convenience tool, but it should not be presented as a production-grade secret vault. Anyone with access to the browser profile may be able to access stored data.

10. Final project: build something real

Choose one project and apply the course from discovery through a working request.

Weather dashboard

Search a city, call a weather API, validate the response, and display current conditions.

AI study helper

Send a prompt through a documented AI API and show the response with usage/error handling.

Image utility

Use an image API to search, transform, or classify images and build a simple result gallery.

Research dashboard

Combine a data API with charts, caching, and clear source attribution.

Project checklist

  1. Define the feature and expected workload.
  2. Find at least three candidate APIs.
  3. Record authentication, free allowance, rate limits, and terms from provider sources.
  4. Test a real request.
  5. Keep secrets out of public source.
  6. Handle non-2xx responses.
  7. Validate returned data.
  8. Document the provider/version you integrated.
  9. Create a fallback or replacement plan if the feature matters.
You are finished when: another developer can understand the integration, obtain their own credentials when required, run it safely, and understand its current limits.
