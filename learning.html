1. Your First API: What Are You Actually Doing?

By the end, you can explain an API and identify the client, server, endpoint, request, and response.

Start here: No programming experience is required. We begin with a restaurant analogy.

Step 1 — Imagine ordering food

You tell a waiter what you want. The waiter takes the order to the kitchen and brings the result back. You = client, waiter = API, kitchen = server, order = request, meal = response.

Step 2 — Translate the analogy

Client

Your website, script, mobile app, or backend.

Server

The system that receives the request and does the work.

Endpoint

A specific API address such as /weather.

Request

What your program sends.

Response

What the API sends back.

Step 3 — Read a request

GET https://api.example.com/weather?city=Bengaluru

GET means retrieve. /weather identifies the operation. city=Bengaluru supplies a value.

Step 4 — Read the response

{ "city": "Bengaluru", "temperature_c": 27.4, "conditions": "Cloudy" }

Your program can turn these values into a card, chart, alert, or recommendation.

Do this now: Explain the restaurant analogy out loud, then explain an API without using the word “API.”
Common mistake: An API is not necessarily a database. Behind an API can be a database, calculation, AI model, or several services.
Checkpoint: In GET /books/42, what is /books/42?
It is the endpoint/path identifying the requested resource: book 42.

2. Sending a Request: HTTP From Zero

Learn the four pieces you see constantly: method, URL, headers, and body.

Step 1 — Start with the URL

https://api.example.com/v1/books

https:// is the protocol, api.example.com is the host, and /v1/books is the path.

Step 2 — Choose the method

MethodBeginner translation
GETGive me information.
POSTHere is data; create/process it.
PUTReplace this resource.
PATCHChange part of this resource.
DELETERemove this resource.

Step 3 — Query parameters

GET /books?author=tolkien&limit=10

? starts the query string and & separates parameters.

Step 4 — Headers

Accept: application/json
Authorization: Bearer YOUR_TOKEN

Headers carry metadata or credentials. The exact names depend on the provider.

Step 5 — Request body

{ "name": "Aryan", "email": "example@email.com" }

A body carries structured data you are sending, commonly with POST, PUT, or PATCH.

Practice: Label POST https://api.example.com/users: POST = method, URL = destination, JSON = body.
Common mistake: Never assume an endpoint accepts every method. Follow its documentation.

3. Reading Responses Without Getting Lost

Learn to tell whether a request worked and how to safely read JSON.

Step 1 — Check the status code

CodePlain English
200Success.
201Created successfully.
400Your request is invalid.
401Authentication is missing/invalid.
403You are not allowed to do that.
404Resource/endpoint not found.
429Too many requests.
500+Server-side failure.

Step 2 — Read JSON

{ "name": "Ada", "age": 36, "skills": ["math", "programming"], "student": false }

name is text, age a number, skills an array, and student a boolean.

Step 3 — Validate important fields

if (typeof data.temperature_c !== "number") {
  throw new Error("Temperature is missing");
}

APIs can omit fields or return null. Robust applications check what they receive.

Step 4 — Separate request failure from data problems

A 401 is an authentication problem. A 200 with an unexpected field is a response-shape problem. Different symptoms need different debugging.

Practice: For HTTP 429, investigate rate limits and quota before changing your JSON parser.
Checkpoint: What should you check first for a 401?

4. API Keys and Authentication — Step by Step

Understand why credentials exist, where they go, and how to protect private secrets.

Step 1 — Why keys exist

Providers may use credentials to identify an application, apply quotas, control access, and reduce abuse.

Step 2 — Recognize common formats

X-API-Key: YOUR_KEY

Authorization: Bearer YOUR_TOKEN

These are examples, not universal rules. Always follow provider documentation.

Step 3 — Distinguish public and private credentials

Some credentials are intentionally browser-safe and restricted. A private server secret is different: it should not be shipped to every visitor.

Step 4 — Store a server secret safely

# .env
API_KEY=your-real-secret

# server-side code
const key = process.env.API_KEY;

Production apps should use the hosting platform's secret/environment system or a secret manager.

Step 5 — If a key leaks

  1. Assume it is compromised.
  2. Revoke/rotate it.
  3. Remove it from exposed code/history where appropriate.
  4. Check logs, screenshots, builds, and repositories.
  5. Replace it with a safer credential flow.
Common mistake: Renaming or hiding a key in frontend JavaScript does not make it secret. Browser-delivered code can be inspected.
Exercise: Pick one directory provider and write down its authentication method, where the credential goes, whether it is required, and whether browser use is supported.

5. “Free” Does Not Always Mean the Same Thing

Learn how to investigate a free API before building around it.

Step 1 — Identify what is actually free

Ask: permanent free tier, recurring quota, temporary trial, free credits, or community endpoint? Is a card required? Does the free allowance cover your endpoint?

Step 2 — Learn four kinds of limits

Quota

Total included in a period.

Rate limit

How quickly requests may be sent.

Endpoint limit

A specific operation may have its own cap.

Credits

Usage may consume a balance instead of simple requests.

Step 3 — Calculate your workload

If one user generates 20 requests/day and you expect 100 users:

20 × 100 × 30 = 60,000 requests/month

This is only a request-count estimate. You still need to check rate limits, endpoint limits, tokens, and terms.

Step 4 — Verify with the provider

Use this directory for discovery, then read the provider's current official pricing, limits, authentication, and terms pages before relying on a quota.

Exercise: Pick one provider and create a five-line free-tier card: authentication, allowance, rate limit, card/account requirement, and official source checked.
Common mistake: “Free” does not mean unlimited.

6. Choosing an API: A Repeatable Process

Learn how to choose based on requirements rather than a free badge.

Step 1 — Describe your feature

Instead of “I need an AI API,” write “I need to classify 5,000 short messages each month and receive a label within two seconds.” Requirements make comparison possible.

Step 2 — Write your constraints

  • What data do you need?
  • How many requests?
  • Browser or server?
  • Commercial use?
  • Region?
  • Latency?
  • Can users provide their own key?

Step 3 — Discover candidates

Use the Use Case Explorer, then the Finder to narrow candidates.

Step 4 — Verify

Check authentication, allowance, limits, endpoints, terms, browser restrictions, and current official documentation.

Step 5 — Test a tiny proof of concept

Make one real request. Measure response time, inspect the response, and intentionally test one failure.

Exercise: Compare two candidates in a table with capability, authentication, free allowance, rate limit, browser support, terms, documentation, and evidence date.

7. Build Your First Integration From Scratch

Go from “I found an API” to “my program uses it safely.”

Step 1 — Read the endpoint documentation

Find the URL, method, parameters, authentication, response format, and errors before coding.

Step 2 — Make the smallest request

async function getWeather(city) {
  const url = "https://api.example.com/weather?city=" + encodeURIComponent(city);
  const response = await fetch(url);
  if (!response.ok) throw new Error("HTTP " + response.status);
  return await response.json();
}

Step 3 — Inspect the real response

Do not invent field names. Look at the actual response and identify the values you need.

Step 4 — Transform provider data

const result = {
  city: data.city,
  temperature: data.temperature_c,
  summary: data.conditions
};

Step 5 — Add failure handling

Handle network errors, non-2xx responses, malformed data, timeouts, and rate limits.

Step 6 — Isolate provider-specific code

Keep provider calls inside a small adapter so changing providers later is easier.

Exercise: Pick a keyless public API from the directory and make one page with one input, one button, one loading state, one result, and one error message.

8. Debugging: Find the Broken Layer

Use evidence instead of random edits.

Step 1 — Check the URL

Verify protocol, host, version, path, parameters, and resource IDs.

Step 2 — Check authentication

Confirm whether a credential is needed, whether it is active, and whether it is placed correctly.

Step 3 — Read the exact status code

401, 403, 404, 429, and 500+ suggest different investigations.

Step 4 — Compare against the provider example

Run the smallest documented example and compare it with your request line by line.

Step 5 — Check the environment

Browser CORS, DNS, proxies, firewall rules, environment variables, and deployment configuration can affect results.

ErrorStart here
401Credential and auth format
403Permissions/plan/restrictions
404URL/path/version/resource
429Rate limit/quota/concurrency
5xxProvider status/transient failure
CORSBrowser policy/provider browser support
Exercise: For a fake 429 error, write three possible causes before changing code. This builds evidence-based debugging habits.

9. Security: Protect Keys and User Data

Learn the minimum security habits every API beginner should adopt.

Step 1 — Classify the credential

Determine whether it is intentionally browser-safe or a private server secret.

Step 2 — Keep private secrets server-side

Browser → Your backend → Provider API
          ↑ secret lives here

Step 3 — Control logging

Do not log tokens, Authorization headers, passwords, or unnecessary personal data.

Step 4 — Validate user input

Check size, type, format, and allowed values before forwarding data to another service.

Step 5 — Plan for exposure

Have a rotation/revocation process before a leak occurs.

Common mistake: Base64 encoding, minifying, or renaming a frontend key does not make it secret.
Exercise: Draw your request path and circle where the private credential lives. If it is inside browser-delivered code, reconsider the architecture.

10. Final Guided Project: Build an API-Powered Mini App

Discover, verify, test, integrate, debug, and document one API.

Step 1 — Choose a tiny idea

Try a weather card, quote generator, country lookup, public-data search, simple AI helper, or image search.

Step 2 — Define success

Write: “When I enter X, my application should request Y and display Z.”

Step 3 — Find three candidates

Use the Use Case Explorer and Finder. Record why each candidate fits.

Step 4 — Verify evidence

Check official authentication, free allowance, limits, terms, and endpoint documentation.

Step 5 — Make one real request

Get a successful response before building a large UI.

Step 6 — Build the smallest UI

One input, button, loading state, result, and error message are enough for version one.

Step 7 — Test failure deliberately

Try an invalid parameter or simulated failure and confirm the app responds clearly.

Step 8 — Document it

Explain what it does, which API it uses, authentication, limits, setup, limitations, and official documentation.

Graduation test: Another beginner should be able to follow your README, obtain their own credentials when needed, run the project, understand the limits, and recover from a common error.
